# 1.0.0 — Initial application skeleton

## What changed

Added the `strukt4` application skeleton (`strukt/strukt`, `type: project`),
the create-project counterpart to [`strukt/framework`](../../framework). It is
deliberately thin: the repository tracks only

- `composer.json` — requires `strukt/framework` and declares `path`
  repositories for the framework and its sibling packages;
- `README.md` — getting started, generated layout, and common commands;
- `LICENSE` — MIT;
- `.gitignore` — ignores every generated artifact;
- `bin/clear` — resets the project to its seed state.

A `post-create-project-cmd` hook scaffolds a runnable application by invoking
the framework console:

```sh
vendor/bin/strukt app:make Web
vendor/bin/strukt app:reload
```

`app:make` renders the framework's `templates/app/*` into `app/src/Web` and
`cfg/app.ini`; `app:reload` writes `lib/App/Loader.php`, `index.php`, and
`.env`. The default application name is `Web`, which keeps the `Web\`
namespace clear of the framework's `App\` → `lib/App` autoload mapping.

## Why

`strukt1/strukt-strukt` was the Composer project seed for the original toolkit,
but its committed contents and bootstrapping (`bin/strukt all`) do not map onto
`strukt4`, whose scaffolding is exposed as the `app:make`/`app:reload` console
commands. This provides an equivalent create-project target that reuses that
machinery instead of duplicating it.

## Documentation

`README.md` documents installation, the generated tree, running the app, the
monorepo `path`-repository workflow, and the common console commands.

## Tests

No automated tests: the package is a Composer skeleton, exercised by installing
it (see below). The generated application is covered by the framework test
suite.

## Public API impact

New package. No changes to existing packages.
