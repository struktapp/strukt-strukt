# 1.2.0 — Session auth routes (`/login`, `/logout`, `/profile`, `/user/list`)

## What changed

Added a session-backed authentication surface to the booted
`Web\AuthModule`, layered on the existing SQLite RBAC:

- `Web\AuthModule\Http\NativeSession` — a `Strukt\Session` subclass backed by
  PHP's `$_SESSION`. The parent store keeps values in memory, so
  `new Session($_SESSION)` would discard every write; this store reads and
  writes `$_SESSION` directly (starting the native session on construction) so
  `Strukt\Auth::login()` survives across requests.
- `App\Provider\Auth` — auto-discovered provider that points the router at the
  native store (`router()->session(...)`), resumes the caller from the session
  (`router()->verify(...)`), and maps that user to granted permissions
  (`router()->permissions(...)`). The permission resolver moved here from the
  database provider so all auth wiring lives in one place.
- `App\Provider\Database` — now only opens the default SQLite connection and
  installs/seeds the RBAC schema; its permission-resolver registration was
  removed.
- `Web\AuthModule\Rbac` — added `findUserByEmail()` and `authenticate()`
  (`password_verify` against the stored hash), and extended `seed()` with a
  `user.list` permission and a `user` role plus `user@strukt.test` account.
  Only `admin` is allowed `user.list`.
- `Web\AuthModule\Router\Auth` — the routes:
  - `POST /login` — validates `email`/`password`, persists the session, returns
    the account with its roles and permissions (`401` on bad credentials).
  - `POST /logout` — clears the session.
  - `GET /profile` — `@Auth()`; returns the current account with roles and
    permissions.
  - `GET /user/list` — `@Auth()` + `@Permission(user.list)`; admin-only.

Demo accounts seeded: `admin@strukt.test` and `user@strukt.test`, password
`secret`.

## Why

The RBAC demo proved authorization but had no way to become a user: nothing
persisted a login. Session-backed login/logout plus a guarded admin route
exercises the full loop — credentials, session persistence, user resolution,
and permission gating — on the booted skeleton.

## Documentation

The booted application code lives under `app/` and `lib/`, both git-ignored, so
it is not part of the tracked package; this changelog is the record, as with the
1.1.0 entry. No tracked docs changed.

## Tests

No automated tests in the skeleton (it is a Composer project). Verified by hand
with a cookie jar against a fresh server (database deleted to force a reseed):

- guest `GET /user/list` → `401`.
- `POST /login` as `user@strukt.test` → `200` (`roles:["user"]`,
  `permissions:["user.view"]`); `GET /profile` → `200`; `GET /user/list` →
  `403`.
- `POST /logout` → `200`; `GET /profile` afterwards → `401`.
- `POST /login` as `admin@strukt.test` → `200` (all seven permissions);
  `GET /user/list` → `200` listing all three accounts.
- `POST /login` with a wrong password → `401`.

## Public API impact

Skeleton only, and entirely within git-ignored generated directories. No
changes to the framework or other packages, and no tracked project files
changed apart from this changelog.
